Idea clave

Desfase objeto-relacional

Con JDBC puro hay que convertir a mano cada fila en un objeto y cerrar los recursos. Es código largo y repetitivo.

Entidades

Entidades · Identificadores · @Basic y @Table · @Column · equals y hashCode

Idea clave

Una entidad es una clase Java con @Entity que se guarda como una tabla. Necesita un identificador único, un constructor sin argumentos y equals y hashCode bien hechos.

Modelo de dominio
  • Son los conceptos del problema a resolver: ayudan a comprender el problema y a diseñar la aplicación.
  • Sus elementos son las entidades y las asociaciones.
  • Una entidad es un concepto del «mundo real» con identidad, atributos y asociaciones.

Mapeo de entidad a tabla

Entidad Contacto

Propiedades: id, nombre, apellidos, email, teléfono.

Tabla CONTACTO

Columnas: id, nombre, apellidos, email, teléfono.

Entidad frente a valor

Entidad

Identificador único y ciclo de vida.

Valor

Sin identificador ni ciclo de vida propio. Tipos: basic, embedded, collection.

Requisitos para ser entidad

  • Llevar @Entity.
  • Constructor sin argumentos.
  • Clase de nivel superior (top-level). No enum, interface ni record. No final.
  • Tener un identificador.
  • equals() y hashCode() consistentes.

Lo que queda abierto: ¿serializable?, abstracta o concreta, extender de otra entidad o no, getters y setters. La primera entidad del curso es la clase Producto, con métodos generados con Lombok.

  • Requisitos: único, no nulo, inmutable.
  • Tipos: simples y compuestos.
  • Datos soportados: primitivos (int, long…), wrappers (Integer, Long…), String, Date (util y sql), BigDecimal, BigInteger y UUID.
  • Se pueden generar valores numéricos y UUID con @GeneratedValue(strategy).

Java · una buena aproximación
@Getter
@Setter
@Entity
@Table(name = "student")
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id", nullable = false)
    private Long id;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Student other = (Student) o;
        return id != null && id.equals(other.getId());
    }

    @Override
    public int hashCode() {
        return getClass().hashCode();
    }
}

Repositorio, esquema y carga de datos

Fundamentos de Spring Data JPA · creación de un repositorio

Idea clave

Un repositorio es una interfaz que extiende JpaRepository. Las tablas las puede crear Hibernate o las creas tú con schema.sql.

Repositorios en Spring Data JPA

  • Es la gran diferencia con JPA. Sustituyen al patrón DAO.
  • Son interfaces, no clases, y usan genéricos.
  • Para crear uno: una interfaz que extienda el repositorio base que queramos. Lo ideal es JpaRepository.

¿Quién crea el DDL?

Spring Data JPA… bueno, JPA… bueno, realmente Hibernate. O el programador.

Hibernate genera el DDL

  • spring.jpa.hibernate.ddl-auto: none, create, drop, create-only, create-drop, validate, update
  • También spring.jpa.properties.hibernate.hbm2ddl.auto

Spring Data genera el esquema

  • Ficheros schema.sql y data.sql
  • Por defecto en el classpath: /src/main/resources
  • ddl-auto a none

schema.sql

configura la ubicación

Otras herramientas, que compiten entre sí: Flyway y Liquibase.

Carga inicial de datos

  • Datos maestros: categorías, literales, i18n…
  • Datos de ejemplo: prototipado, testeo…

Asociaciones

ManyToOne · OneToMany · OneToOne · ManyToMany

Idea clave

Las asociaciones conectan entidades: @ManyToOne, @OneToMany, @OneToOne y @ManyToMany. En las bidireccionales hay que mantener coherentes los dos lados.

Las entidades no están aisladas: Producto - Categoría, Producto - LineaVenta, LineaVenta - Venta…

Multiplicidad

  • @ManyToOne / @OneToMany
  • @OneToOne
  • @ManyToMany

Direccionalidad

  • Unidireccional: de A hacia B.
  • Bidireccional: de A hacia B y de B hacia A.
@ManyToOne
  • Es la asociación más común.
  • Equivale a una clave externa (FK) y establece una relación padre / hijo.
  • Se anota con @ManyToOne y @JoinColumn (nombre de la columna y FK, tipo de dato…).

Ejemplo del curso: entidad y repositorio de Categoría, import.sql, y rescatar un producto por ID incluyendo su categoría.

@OneToMany

Unidireccional

  • Sobre una colección, sin @ManyToOne correspondiente.
  • Crea una tabla join.
  • Muy ineficiente.

Bidireccional

  • @ManyToOne + @OneToMany.
  • Mismo DDL que con @ManyToOne a secas.
  • @OneToMany es el lado mapeado.

El atributo mappedBy lleva el nombre del atributo del lado propietario.

toString con recursión infinita

En una bidireccional, el toString de cada lado llama al del otro, sin fin. Dos soluciones:

  • Lombok: @ToString.Exclude sobre el lado mapeado.
  • JPA Buddy.

Sincronización de ambos lados

Hay que mantener coherentes los dos lados (la categoría y su colección de productos). Se hace con métodos auxiliares (helper) que desarrollas tú. En los ejemplos aparecen en el lado mapeado (la colección).

FetchPor ahora todo funciona porque el FetchType es EAGER. Lo ideal es usar LAZY (ver la sección de fetching).
@OneToOne
  • Una instancia de A se relaciona con una sola de B: Usuario - Perfil, Producto - DetalleProducto…
  • Puede ser unidireccional o bidireccional, según convenga a la semántica del problema.
  • Se usa a menudo para desgajar una entidad en dos: los atributos que se leen o modifican siempre, y los que se tocan de vez en cuando.

Se puede mejorar con:

cascade = CascadeType.ALL
ciclo de vida en cascada: cualquier operación sobre Producto afecta a ProductoDescripción
@MapsId
mapea un atributo (clave externa) como identificador; sirve a la vez como PK y FK
@ManyToMany
  • Una instancia de A se relaciona con muchas de B, y una de B con muchas de A: Proyecto - Empleado, Usuario - Producto (me gusta)…
  • Unidireccional o bidireccional, según la semántica del problema.

¿Qué tipo de colección usar?

List (realmente Bag)

  • Más difícil mantener la coherencia.
  • Suele rendir mejor, pero no para el borrado.
  • Puede contener duplicados.

Set

  • Genera el DDL adecuado.
  • Puede rendir peor.
  • No contiene duplicados.

Fetching y operaciones en cascada

Fundamentos de Spring Data JPA · fetching y cascada

Idea clave

EAGER trae los datos siempre. LAZY los trae cuando los usas y necesita la sesión abierta. La cascada pasa una operación del padre a sus hijos.

Fetching

Es la obtención de datos desde la base de datos. Hay que decidir cuándo (¿ahora o más tarde?) y cómo.

FetchType por defecto

  • XXXToOne: EAGER
  • XXXToMany: LAZY

EAGER (ansioso)

Toma todos los datos, se vayan a usar o no.

LAZY (perezoso)

No toma todos los datos al rescatar la entidad. Lo hace cuando se usan (getXXX()) y con la sesión abierta.

Sesión abierta

Opciones para acceder a datos LAZY:

  • Open Session in View (antipatrón).
  • Consultas JOIN FETCH.
  • Acceso dentro de una transacción.
  • Grafos de entidad.
  • Usar EAGER.

Dentro de una transacción: crear un bean (¿servicio?), inyectar el repositorio, anotar con @Transactional(readOnly=true) y cargar la colección LAZY. Con JOIN FETCH: una consulta en CategoriaRepository, se ejecuta y se compara.

Cascada
  • Una acción sobre una entidad se transmite a las relacionadas. Es útil en asociaciones padre/hijo.
  • El atributo cascade está en todas las asociaciones. Es un array de CascadeType: DETACH, MERGE, PERSIST, REFRESH, REMOVE y ALL.
  • Ciclo de vida de una entidad, con las operaciones findById(id), save(entity) y delete(entity).

Tutorial Entity Graphs

Tutorial-Entity_Graphs_Spring_Data_JPA.md

Idea clave

Un Entity Graph cambia el plan de carga solo para una consulta. Así evitas LazyInitializationException y el problema N+1 sin escribir JOIN FETCH.

Los grafos de entidad (Entity Graphs) llegan con JPA 2.1 y Spring Data JPA. Resuelven los problemas de rendimiento al cargar asociaciones.

El problema de fondo

La regla de oro es mapear todas las asociaciones como FetchType.LAZY. Así no se arrastra media base de datos a memoria cada vez que lees una entidad simple. Pero eso trae dos problemas en producción:

  • LazyInitializationException: ocurre al acceder a una relación LAZY (por ejemplo pedido.getLineas()) fuera de una sesión o transacción abierta. Pasa en el controlador o al serializar JSON en una API REST.
  • Problema N+1: si recorres 100 pedidos y accedes a sus clientes LAZY, Hibernate lanza 1 consulta para los pedidos y 100 más para los clientes. Son 101 consultas SQL.

¿Por qué mejor que JOIN FETCH?

JOIN FETCH en JPQL tiene inconvenientes:

  • Acopla la lógica de carga a cadenas JPQL largas.
  • Dificulta reutilizar métodos derivados o estándar de JpaRepository (findAll(), findById()).
  • Combinar varias colecciones List en un solo JOIN FETCH produce el error MultipleBagFetchException.
Qué es un Entity Graph

Una plantilla de lectura dinámica: cambia el plan de carga (fetching plan) solo para una consulta concreta. Sobrescribe de forma temporal el LAZY sin tocar el código del modelo.

Grafos ad hoc con attributePaths

Se definen directamente en el método del repositorio con @EntityGraph. Son ideales para una solución rápida y localizada, sin llenar la entidad de anotaciones.

Ejemplo 1: grafo simple de primer nivel

Cargar un Cliente con su Direccion (@OneToOne) en una sola consulta SQL.

Java
public interface ClienteRepository extends JpaRepository<Cliente, Long> {

    // 'direccion' pasa a EAGER solo para esta consulta
    @EntityGraph(attributePaths = {"direccion"})
    Optional<Cliente> findWithDireccionByEmail(String email);
}
SQL generado por Hibernate
SELECT c.id, c.email, c.nombre, c.direccion_id,
       d.id, d.calle, d.ciudad, d.codigoPostal
FROM clientes c
LEFT OUTER JOIN direcciones d ON c.direccion_id = d.id
WHERE c.email = ?;

Ejemplo 2: rutas compuestas (subgrafos implícitos)

¿Y si al consultar un Pedido quieres sus lineas, el producto de cada línea y la categoria de cada producto? En attributePaths puedes escribir rutas anidadas con notación de punto. Spring Data JPA las traduce a subgrafos.

Java
public interface PedidoRepository extends JpaRepository<Pedido, Long> {

    // 1. En un método derivado por nombre
    // Carga: Pedido -> cliente -> direccion
    //   y también: Pedido -> lineas -> producto -> categoria
    @EntityGraph(attributePaths = {
        "cliente.direccion",
        "lineas.producto.categoria"
    })
    List<Pedido> findByEstado(String estado);

    // 2. En la sobrescritura de un método estándar de JpaRepository
    @Override
    @EntityGraph(attributePaths = {"cliente", "lineas.producto"})
    Optional<Pedido> findById(Long id);

    // 3. En una consulta con @Query explícita
    @EntityGraph(attributePaths = {"lineas.producto.etiquetas"})
    @Query("SELECT p FROM Pedido p WHERE p.total > :minimo")
    List<Pedido> buscarPedidosGrandesConEtiquetas(@Param("minimo") BigDecimal minimo);
}
Grafos con nombre

Cuando la estructura de lectura es compleja o se repite en varios repositorios, lo mejor es declarar un grafo con nombre sobre la clase @Entity.

@NamedEntityGraph
define el grafo raíz sobre la entidad. Tiene name (nombre del grafo), attributeNodes (atributos de primer nivel, con @NamedAttributeNode) y subgraphs (subgrafos para profundizar).
@NamedSubgraph
especifica qué atributos cargar dentro de una entidad relacionada.

Ejemplo completo: Pedido.completoConDetalles

Un grafo reutilizable que carga:

  • el cliente del pedido y la direccion de ese cliente;
  • las lineas, el producto de cada línea, la categoria del producto y sus etiquetas (@ManyToMany).
Java · sobre la entidad Pedido
@Entity
@Table(name = "pedidos")
@NamedEntityGraph(
    name = "Pedido.completoConDetalles",
    attributeNodes = {
        // atributo simple, con subgrafo hasta la dirección del cliente
        @NamedAttributeNode(value = "cliente", subgraph = "subgrafo-cliente-direccion"),
        // colección, con subgrafo para navegar por las líneas
        @NamedAttributeNode(value = "lineas", subgraph = "subgrafo-lineas-producto")
    },
    subgraphs = {
        // Subgrafo 1: Cliente -> Direccion
        @NamedSubgraph(name = "subgrafo-cliente-direccion",
            attributeNodes = { @NamedAttributeNode("direccion") }),
        // Subgrafo 2: LineaPedido -> Producto
        @NamedSubgraph(name = "subgrafo-lineas-producto",
            attributeNodes = { @NamedAttributeNode(value = "producto",
                                 subgraph = "subgrafo-producto-detalles") }),
        // Subgrafo 3: Producto -> Categoria y Etiquetas
        @NamedSubgraph(name = "subgrafo-producto-detalles",
            attributeNodes = { @NamedAttributeNode("categoria"),
                               @NamedAttributeNode("etiquetas") })
    }
)
public class Pedido {
    // Campos y relaciones mapeados antes...
}

Herencia

MappedSuperclass · Single Table · Joined · Table Per Class

Idea clave

Las bases de datos relacionales no tienen herencia. Hay cuatro formas de guardarla: MappedSuperclass, Single Table, Joined y Table Per Class.

  • La herencia es un mecanismo de la orientación a objetos (relación es-un): una clase extendida recibe atributos y métodos de una base.
  • Las bases de datos relacionales no soportan herencia, así que hay que trasladarla a estructuras relacionales.
EstrategiaCómo se guarda
MappedSuperclassLa clase base no es entidad. Hay herencia en Java, pero no se refleja en la base de datos.
Single TableClase y subclases en una sola tabla. Es la opción por defecto.
JoinedUna tabla por clase. Las hijas llevan sus atributos y la FK a la base.
Table Per ClassUna tabla por subclase, con los atributos base más los propios. Sin FK.
MappedSuperclass

La «entidad» base reúne lo común sin ser entidad: id, hashCode, auditoría (creador, fecha…).

Single Table
  • Cada subclase declara sus propias propiedades persistentes.
  • En la clase base: @Inheritance(strategy = InheritanceType.SINGLE_TABLE), @DiscriminatorColumn y @DiscriminatorValue.
  • Repositorio polimórfico: UsuarioRepository.save(administrador).

Ejemplo del curso: Administrador extiende a Usuario, con un único atributo.

Joined
  • Tabla base con los atributos de la clase. Tablas hijas con los atributos de las subclases más la FK a la base.
  • Se anota en la clase base con @Inheritance(strategy = InheritanceType.JOINED).
  • Guardar un empleado: 1 INSERT. Guardar un gerente: 2 INSERT.
SQL · EMPLEADO(id, nombre, email, teléfono, departamento) y GERENTE(id, tieneMBA)
INSERT INTO EMPLEADO VALUES (1, 'Pepe', …);
INSERT INTO GERENTE VALUES (1, true);

SELECT *
FROM empleado JOIN gerente …

Consultas polimórficas

No hace falta un repositorio por clase: se puede trabajar con el de la clase base.

JPQL

-- Versión 2: TYPE(entity)

Table Per Class
  • Inversa a Joined: las subclases incluyen los atributos de la base más los propios. No hay FK.
  • Guardar una vivienda (alquiler o venta): 1 insert. Las consultas polimórficas usan UNION ALL.

Consultas polimórficas: Table Per Class sí, MappedSuperclass no.

¿Cuándo usar Table Per Class?

  • Necesitas alguna consulta polimórfica (no muchas).
  • Las subclases tienen asociaciones por separado.

Consultas JPQL

Fundamentos de Spring Data JPA · JPQL

Idea clave

JPQL se parece a SQL, pero habla de entidades y atributos, no de tablas y columnas. Se escribe con @Query sobre un método del repositorio.

  • Jakarta (antes Java) Persistence Query Language: lenguaje de consulta orientado a objetos, basado en SQL y muy parecido a él.
  • Trabaja con objetos, no con tablas ni columnas. Abstrae la base de datos y soporta operaciones CRUD.
  • Con JPA/Hibernate: objetos Query / TypedQuery, y consultas estáticas con @NamedQuery.
  • Con Spring Data JPA: anotación @Query en un método del repositorio. Y ya está.
  • Tipos de consulta: select, update, delete, insert … values e insert … select.

Literales

  • Booleanos: true, false. Cadenas entre comillas simples. Numéricos.
  • Fecha y hora con sintaxis de escape JDBC: {d 'yyyy-mm-dd'} y {ts 'yyyy-mm-ddThh:mm:ss'}.
  • Enumeración: no hace falta el tipo como prefijo, se infiere de la consulta.
JPQL
WHERE o.status = SHIPPED

Funciones: conversiones de tipos, valores nulos, fechas y horas, cadenas y numéricas.

Consultas nativas

Se puede usar SQL nativo, útil en situaciones concretas. No abusar.

Java
@Query("...", nativeQuery = true)

SELECT básico

JPQL
SELECT …
FROM …
[WHERE …]
  • DISTINCT deja un valor de los iguales. Tiene sentido al hacer JOIN y en consultas escalares.
  • Agregación: COUNT(..), MAX(...), MIN(...), AVG(...) y SUM(...). Devuelven un valor escalar.
  • Proyecciones con constructor: se obtiene un DTO con datos parciales de una entidad. Hace falta un constructor con los argumentos necesarios.

Cláusula FROM

Determina la entidad a consultar.

JOIN [FETCH]
reunión con una asociación. Con FETCH se incluyen también los datos de la asociación
LEFT JOIN [FETCH]
por defecto JOIN es INNER JOIN: una entidad sin correspondencia no sale. LEFT da el OUTER JOIN

Cláusula WHERE

  • Añade condiciones con valores literales o con parámetros de la función de consulta.
  • Operadores habituales: =, <, >, <=, >=, != o <>, LIKE, BETWEEN, IS NULL, IN. Otros: IS TRUE/FALSE, MEMBER OF…

Parámetros, dos estilos: posicional (?1, ?2) o por nombre (:nombre, :precio). Con nombre, @Param si la variable y la expresión no coinciden.

Ejercicios propuestos: el precio más caro de la categoría Electrónica, productos que incluyen algunos tags de una lista, y los productos con «Inalámbrico» y precio entre 20 y 50 €.

Tutorial JPQL con @Query

Tutorial-Consultas_JPQL_Spring.md

Idea clave

Con @Query escribes la consulta JPQL encima del método del repositorio. Aquí hay 10 consultas de ejemplo con un comercio electrónico: filtros, joins, paginación y DTO.

JPQL trabaja sobre el modelo de objetos (entidades y atributos Java), no sobre tablas y columnas. En Spring Boot, @Query sobre la interfaz del repositorio es la forma preferida por su legibilidad, flexibilidad y mantenimiento.

Dominio de ejemplo

Todos los ejemplos usan un comercio electrónico:

Categoria
id, nombre
Producto
id, nombre, precio, categoria (@ManyToOne)
Cliente
id, nombre, email, activo
Pedido
id, fecha, total, estado, cliente (@ManyToOne)
Parámetros y filtrado

Una consulta simple se puede derivar del nombre del método (findByEmail). Cuando necesitas precisión o claridad, escribes el JPQL con @Query. Hay dos formas de pasar parámetros:

  • Posicionales (?1, ?2): coinciden con el orden de los argumentos del método.
  • Con nombre (:parametro): se enlazan con @Param("parametro"). Son más legibles y resisten los cambios de orden.
Java · derivada frente a JPQL
public interface ClienteRepository extends JpaRepository<Cliente, Long> {

    // 1. Derivada: Spring deduce la consulta por el nombre
    Optional<Cliente> findByEmailAndActivoTrue(String email);

    // 2. JPQL con @Query: consulta explícita y equivalente
    @Query("SELECT c FROM Cliente c WHERE c.email = :email AND c.activo = true")
    Optional<Cliente> buscarPorEmailActivo(@Param("email") String email);

    // 3. JPQL con parámetro posicional
    @Query("SELECT c FROM Cliente c WHERE c.nombre LIKE %?1% AND c.activo = true")
    List<Cliente> buscarActivosPorNombreParcial(String parteNombre);
}

En SELECT c FROM Cliente c, c es un alias de la entidad Cliente. La consulta devuelve instancias completas de Cliente.

Relaciones y joins

JPQL permite navegar por los atributos de relación con el punto (.) o con JOIN. Hay dos tipos fundamentales:

  • JOIN simple (INNER JOIN / LEFT JOIN): filtra la entidad principal según los atributos de la relacionada.
  • JOIN FETCH: carga la asociación diferida (lazy) en la misma consulta SQL. Evita el problema de las N+1 consultas y las excepciones LazyInitializationException fuera de la transacción.
Java · filtrar por relación y JOIN FETCH
public interface ProductoRepository extends JpaRepository<Producto, Long> {

    // A) Derivada que navega Producto -> Categoria -> Nombre
    List<Producto> findByCategoria_Nombre(String nombreCategoria);

    // B) Equivalente en JPQL con JOIN explícito
    @Query("SELECT p FROM Producto p JOIN p.categoria c WHERE c.nombre = :nombreCategoria")
    List<Producto> buscarPorNombreCategoria(@Param("nombreCategoria") String nombreCategoria);

    // C) JOIN FETCH: productos y su Categoria en un solo SELECT
    @Query("SELECT p FROM Producto p JOIN FETCH p.categoria WHERE p.precio >= :precioMinimo")
    List<Producto> buscarProductosConCategoriaCargada(@Param("precioMinimo") Double precioMinimo);
}
Consejo de rendimientoSi vas a usar producto.getCategoria().getNombre() después de la consulta y la relación es FetchType.LAZY, usa JOIN FETCH para traer todo en una sola llamada a la base de datos.
Operadores y funciones
  • IN: el atributo coincide con algún elemento de una lista o colección pasada como parámetro.
  • MEMBER OF: un elemento pertenece a una colección mapeada en la entidad.
  • Funciones de cadena: UPPER(), LOWER(), CONCAT(), SUBSTRING(), TRIM(), LENGTH().
  • Funciones numéricas y de fecha: ABS(), ROUND(), MOD(), CURRENT_DATE, CURRENT_TIME, EXTRACT().
  • Funciones para nulos: COALESCE(x, y) devuelve el primer valor no nulo. También NULLIF(x, y).

Se pueden usar en WHERE, HAVING y SELECT.

Las 10 consultas imprescindibles

1. Selección por atributos con parámetros con nombre

Caso de uso: recuperar una entidad por coincidencia exacta en uno o más atributos.

Java
@Query("SELECT c FROM Cliente c WHERE c.email = :email AND c.activo = true")
Optional<Cliente> buscarClienteActivoPorEmail(@Param("email") String email);

Lección clave: SELECT c FROM Cliente c selecciona la instancia completa de Cliente, representada por el alias c.

2. Búsqueda de texto parcial, sin distinguir mayúsculas

Caso de uso: un buscador de productos donde el usuario escribe un término. Se combinan LOWER(), CONCAT() y LIKE.

Java
@Query("SELECT p FROM Producto p WHERE LOWER(p.nombre) LIKE LOWER(CONCAT('%', :termino, '%'))")
List<Producto> buscarPorNombreContiene(@Param("termino") String termino);

Lección clave: con CONCAT('%', :termino, '%') no hace falta concatenar los signos % a mano en la capa de servicio.

3. Navegar una @ManyToOne con JOIN

Caso de uso: filtrar Producto por propiedades de su Categoria.

Java
@Query("SELECT p FROM Producto p JOIN p.categoria c WHERE c.nombre = :nombreCategoria")
List<Producto> buscarPorNombreCategoria(@Param("nombreCategoria") String nombreCategoria);

Lección clave: p.categoria es el atributo de relación. Con JOIN p.categoria c creas el alias c para acceder a los campos de Categoria.

4. Cargar asociaciones diferidas con JOIN FETCH

Caso de uso: evitar LazyInitializationException y el problema N+1 al recuperar pedidos y sus clientes. Si accedes a pedido.getCliente().getNombre() fuera de la transacción con una relación LAZY, falla.

Java
@Query("SELECT p FROM Pedido p JOIN FETCH p.cliente WHERE p.estado = :estado")
List<Pedido> buscarPedidosConClienteCargado(@Param("estado") String estado);

Lección clave: FETCH hace que Hibernate cargue en memoria el Cliente dentro de cada Pedido, en una sola consulta SQL.

5. Filtrar por una colección de valores (IN)

Caso de uso: pedidos cuyo estado sea cualquiera de una lista (por ejemplo "PENDIENTE" o "EN_PROCESO"). JPQL traduce IN y la colección Java a IN (?, ?, ...).

Java
@Query("SELECT p FROM Pedido p WHERE p.estado IN :estados")
List<Pedido> buscarPorEstados(@Param("estados") Collection<String> estados);

Lección clave: el parámetro puede ser cualquier Collection<T>: un List, un Set…

6. Rangos de fechas y valores (BETWEEN)

Caso de uso: un informe de ventas entre dos fechas con un importe mínimo. Se combina BETWEEN con >= y <=.

Java
@Query("SELECT p FROM Pedido p WHERE p.fecha BETWEEN :desde AND :hasta AND p.total >= :totalMinimo")
List<Pedido> buscarPedidosEnRangoYTotal(
        @Param("desde") LocalDateTime desde,
        @Param("hasta") LocalDateTime hasta,
        @Param("totalMinimo") BigDecimal totalMinimo);

Lección clave: BETWEEN incluye los extremos. JPQL maneja de forma nativa los tipos de java.time (LocalDateTime, LocalDate).

7. Valores nulos y valores por defecto (COALESCE)

Caso de uso: filtrar productos sin que los precios nulos excluyan registros por error. COALESCE(expresion, valorPorDefecto) devuelve el valor alternativo si la expresión es NULL.

Java
@Query("SELECT p FROM Producto p WHERE COALESCE(p.precio, 0) <= :precioMaximo")
List<Producto> buscarPorPrecioMaximoSeguro(@Param("precioMaximo") BigDecimal precioMaximo);

Lección clave: evita que los nulos de la base de datos estropeen las comparaciones del WHERE.

8. Subconsultas y existencia (EXISTS)

Caso de uso: clientes con al menos un pedido cuyo total supere una cantidad. Es útil cuando filtras la entidad principal según si tiene registros asociados que cumplen una condición, sin cargar los hijos en memoria.

Java
@Query("SELECT c FROM Cliente c WHERE EXISTS (" +
       "  SELECT p FROM Pedido p WHERE p.cliente = c AND p.total > :montoMinimo" +
       ")")
List<Cliente> buscarClientesConPedidosMayoresA(@Param("montoMinimo") BigDecimal montoMinimo);

Lección clave: la subconsulta usa la entidad externa c. EXISTS devuelve true en cuanto encuentra una coincidencia, así que es muy eficiente.

9. Consultas paginadas con Pageable y Page

Caso de uso: listar los productos de una categoría en páginas de 10 elementos. Con un parámetro Pageable en un método con @Query, Spring Data aplica paginación y orden a la consulta.

Java
@Query("SELECT p FROM Producto p WHERE p.categoria.id = :categoriaId")
Page<Producto> buscarPorCategoriaPaginado(
        @Param("categoriaId") Long categoriaId,
        Pageable pageable);

// En la capa de servicio
Pageable paginacion = PageRequest.of(0, 10, Sort.by("nombre").ascending());
Page<Producto> pagina = productoRepository.buscarPorCategoriaPaginado(2L, paginacion);

Lección clave: no escribes LIMIT ni OFFSET en JPQL. Spring Data genera el SQL de paginación y ejecuta por detrás la consulta COUNT para construir el Page.

Caso de uso: una tabla resumen de pedidos en una pantalla de administración, sin cargar objetos completos de Cliente ni Pedido. Un DTO (Data Transfer Object) es un objeto ligero que no es entidad. Se crea con SELECT new com.paquete.DTO(...).

Complejidad
Derivadas: ideales para consultas con 1 o 2 condiciones.

Consultas con @Modifying

Fundamentos de Spring Data JPA · DML

Idea clave

Para modificar datos con @Query hace falta @Modifying. Estas consultas no respetan el ciclo de vida de la entidad.

Hasta ahora, consultas DQL (Data Query Language). ¿Y las DML (INSERT, UPDATE, DELETE)? Mecanismos: consultas derivadas, @Query y customización del repositorio.

DML con consultas derivadas

  • Empiezan por deleteBy… y siguen con un predicado.
  • Requieren @Transactional.
  • Ejemplo: deleteByPrecioVentaGreaterThan(...)
  • Ventaja: conectan con el ciclo de vida. Al eliminar Producto, elimina ProductoDescripcion.
  • Desventaja: solo borran. No insertan ni actualizan.

DML con @Query

  • Sin @Modifying da error: InvalidDataAccessApiUsageException.
  • Con @Modifying son operaciones BULK: no se hacen entidad a entidad.
  • Dificultad: no respetan el ciclo de vida.

Ejercicios propuestos: incrementar el precio de todos los productos en un %, y decrementar el de todos los de una categoría en un %.

En resumenLas consultas derivadas están conectadas al ciclo de vida. Las @Query con @Modifying son potentes pero no están conectadas al ciclo de vida.

Paginación y ordenación

Fundamentos de Spring Data JPA · paginación, Limit y Sort

Idea clave

Pageable pide los datos por páginas y devuelve un Page. Sort ordena y Limit limita el número de resultados.

Paginación

findAll() puede ser un antipatrón: ¿10 filas?, ¿1000?, ¿1 000 000? Paginar es obtener un conjunto limitado de resultados e incluir la información para llegar a los conjuntos adyacentes. Se usa PagingAndSortingRepository.

Java
Page<T> findAll(Pageable p)

// También en cualquier otra consulta
Page<T> findByCategoria(Categoria c, Pageable p)

@Query("""select p from Producto p
         where p.precioVenta > :precio""")
Page<T> porPrecio(double precio, Pageable p)

Pageable

Elemento de entrada para paginar: número de página, tamaño de página y ordenación.

Page<T>

Resultado de una consulta paginada: un subconjunto del resultado completo, con información para navegar a otras páginas.

Warning de Hibernate«firstResult/maxResults specified with collection fetch; applying in memory!». La consulta incluye una colección y, si pagina, los tags pueden quedar a medias. Soluciones: caché de 1.er nivel y dos consultas, o una consulta compleja.
Limit

Disponible desde Spring Boot 3.2. Limita los resultados devueltos con Limit.of(cantidad) o Limit.unlimited().

Ordenación

Hasta ahora, order by en consultas derivadas (…OrderBy…) y en JPQL. Sort permite ordenar en cualquier consulta: indicar propiedades y dirección (asc, desc).

  • by(...): lista de atributos, dirección y atributos, o lista de Sort.Order (dirección + atributo).
  • and() combina dos Sort.
  • ascending() y descending() convierten un Sort en ascendente o descendente.
Java · Sort, Limit y Pageable
// Sort y Limit se combinan sin problema
List<T> consulta(Sort s, Limit l)

// ¡Error!
Page<T> query(Pageable p, Sort s)

// Correcto: Sort como argumento de Pageable
PageRequest.of(n, s, Sort.by(...))

Estrategias de búsqueda

El proxy del repositorio puede derivar la consulta del nombre del método o usar una consulta definida a mano. Se elige con queryLookupStrategy de @EnableJpaRepositories (o query-lookup-strategy en XML).

CREATE
construye la consulta a partir del nombre del método, quitando los prefijos conocidos
USE_DECLARED_QUERY
usa una consulta declarada (por ejemplo, con una anotación). Si no hay ninguna, el arranque falla
CREATE_IF_NOT_FOUND
la opción por defecto: busca una consulta declarada y, si no existe, usa CREATE
Creación de consultas por nombre
Java
interface PersonRepository extends Repository<Person, Long> {

  List<Person> findByEmailAddressAndLastname(EmailAddress emailAddress, String lastname);

  // distinct
  List<Person> findDistinctPeopleByLastnameOrFirstname(String lastname, String firstname);

  // ignorar mayúsculas en una propiedad o en todas
  List<Person> findByLastnameIgnoreCase(String lastname);
  List<Person> findByLastnameAndFirstnameAllIgnoreCase(String lastname, String firstname);

  // ORDER BY estático
  List<Person> findByLastnameOrderByFirstnameAsc(String lastname);
  List<Person> findByLastnameOrderByFirstnameDesc(String lastname);
}
  • El nombre se divide en sujeto (find…By, exists…By) y predicado (lo que va tras el primer By).
  • El texto entre find y By es descriptivo, salvo que lleve Distinct o Top/First.
  • Las condiciones se unen con And y Or.
  • El orden estático usa OrderBy con Asc o Desc. Para orden dinámico, usa Sort.

Nombres reservados

Los métodos heredados, como CrudRepository#findById, siempre apuntan a la propiedad identificador, sea cual sea el nombre del atributo. Lo mismo vale para exists y delete. Reservados: deleteAllById, deleteById, existsById, findAllById y findById.

Java
class User {
  @Id Long pk;     // el identificador
  Long id;         // una propiedad llamada id, pero no es el identificador
}

interface UserRepository extends Repository<User, Long> {
  Optional<User> findById(Long id);      // resuelve a pk, es el método reservado
  Optional<User> findByPk(Long pk);     // consulta derivada sobre pk
  Optional<User> findUserById(Long id); // el texto entre find y By apunta a id
}

Expresiones de propiedad

Pueden recorrer propiedades anidadas. Con findByAddressZipCode primero busca una propiedad addressZipCode; si no existe, divide el nombre por mayúsculas desde la derecha (AddressZip + Code, luego Address + ZipCode). Si hay ambigüedad, marca el punto de recorrido con un guion bajo:

Java
List<Person> findByAddressZipCode(ZipCode zipCode);
List<Person> findByAddress_ZipCode(ZipCode zipCode);

El guion bajo está reservado, así que se recomienda el camelCase estándar de Java.

Streamable y Stream

Java · concatenar resultados con Streamable
interface PersonRepository extends Repository<Person, Long> {
  Streamable<Person> findByFirstnameContaining(String firstname);
  Streamable<Person> findByLastnameContaining(String lastname);
}

Streamable<Person> result = repository.findByFirstnameContaining("av")
  .and(repository.findByLastnameContaining("ea"));
  • Un tipo propio puede ser tipo de retorno si implementa Streamable y tiene un constructor o un método estático of(…)/valueOf(…) que reciba un Streamable.
  • Un Stream envuelve recursos del almacén (como un ResultSet), así que necesita una transacción y hay que cerrarlo.
  • Usar Stream no garantiza lectura incremental. Para conjuntos grandes, usa query hints con el tamaño de fetch del proveedor.
Java
@Transactional
public void processUsers() {
  try (Stream<User> users = repository.streamByFirstnameAndLastname("John", "Doe")) {
    // consumir el stream
  }
}

Java · parámetros especiales

  • Sort, Pageable y Limit no pueden ser null. Para omitirlos: Sort.unsorted(), Pageable.unpaged(), Limit.unlimited().
  • Page conoce el total de elementos y páginas, lo que cuesta una consulta de conteo extra. Slice solo sabe si hay otro trozo y evita ese conteo. List limita al rango pedido sin metadatos.
  • Cada parámetro especial se usa una sola vez por método.
  • Combinaciones no válidas: Pageable con Sort (el Pageable ya define el orden) y Pageable con Limit (ya define el límite).
  • Top se puede combinar con Pageable: Top fija el máximo total y Pageable puede reducirlo más.

Consultas declaradas

Named queries

Se resuelven por convención: <NombreSimpleDeLaEntidad>.<método>, por ejemplo User.findByLastname. Deben ser JPQL. @NamedNativeQuery permite SQL nativo a costa de perder portabilidad.

Java
@Entity
@NamedQuery(name = "User.findByEmailAddress",
  query = "select u from User u where u.emailAddress = ?1")
public class User { }

La anotación evita editar otro fichero, pero obliga a recompilar la entidad por cada consulta nueva. También se pueden definir en orm.xml (carpeta META-INF) con <named-query />.

@Query

Une la consulta al método y mantiene los detalles de persistencia fuera de la entidad. Tiene prioridad sobre @NamedQuery y orm.xml.

Java
@Query("select u from User u where u.emailAddress = ?1")
User findByEmailAddress(String emailAddress);

// LIKE avanzado: se reconoce el % y se aplica al parámetro
@Query("select u from User u where u.firstname like %?1")
List<User> findByFirstnameEndsWith(String firstname);

Consultas nativas

@NativeQuery es casi una anotación compuesta de @Query(nativeQuery=true) y añade atributos como sqlResultSetMapping. Spring Data reescribe consultas simples para paginar y ordenar. Las complejas necesitan JSqlParser en el classpath o un countQuery.

Java
@NativeQuery(value = "SELECT * FROM USERS WHERE LASTNAME = ?1",
  countQuery = "SELECT count(*) FROM USERS WHERE LASTNAME = ?1")
Page<User> findByLastname(String lastname, Pageable pageable);

// pares columna/valor en bruto (solo Hibernate)
@NativeQuery("SELECT * FROM USERS WHERE EMAIL_ADDRESS = ?1")
Map<String, Object> findRawMapByEmail(String emailAddress);

Parámetros con nombre

Por defecto el enlace es posicional. @Param enlaza un parámetro del método con uno con nombre. Con el flag de compilador -parameters se puede omitir @Param.

Java
@Query("select u from User u where u.firstname = :firstname or u.lastname = :lastname")
User findByLastnameOrFirstname(@Param("lastname") String lastname,
                               @Param("firstname") String firstname);

Expresiones SpEL en @Query

  • #{#entityName} resuelve al nombre de la entidad (o al nombre simple de la clase). Sirve para repositorios genéricos con herencia.
  • Los argumentos se leen por índice: ?#{[0]}.
  • El comodín % se puede poner delante o detrás de un parámetro o expresión: like %:#{[0]}%.
  • Para entrada no fiable en un like, usa escape([0]) junto con la cláusula escape y escapeCharacter().
  • Se pueden leer propiedades de configuración: ?${spring.application.name:unknown}.
Java
@Query("select u from #{#entityName} u where u.lastname = ?1")
List<User> findByLastname(String lastname);

@Query("select u from User u where u.firstname like %?#{escape([0])}% escape ?#{escapeCharacter()}")
List<User> findContainingEscaped(String namePart);

Ordenar con Sort en @Query

Las propiedades del Sort deben resolver a una propiedad o a un alias de la consulta. Una llamada a función se rechaza, salvo que uses JpaSort.unsafe.

Java
repo.findByAndSort("lannister", Sort.by("firstname"));                // válido
repo.findByAndSort("stark", Sort.by("LENGTH(firstname)"));            // inválido: lanza excepción
repo.findByAndSort("targaryen", JpaSort.unsafe("LENGTH(firstname)")); // válido, explícitamente unsafe
repo.findByAsArrayAndSort("bolton", Sort.by("fn_len"));               // válido: alias de una función

JpaSort.unsafe admite funciones, CASE WHEN, aritmética y rutas de propiedad. No admite subconsultas, TREAT ni CAST.

Modificar datos
Java
@Modifying
@Query("update User u set u.firstname = ?1 where u.lastname = ?2")
int setFixedFirstnameFor(String firstname, String lastname);
  • @Modifying convierte la consulta en un update en lugar de un select. Solo se usa con @Query.
  • No limpia el EntityManager automáticamente, porque perdería cambios pendientes. Con clearAutomatically = true sí lo limpia.
deleteByRoleId · derivado
void deleteByRoleId(long roleId);
deleteInBulkByRoleId · bulk
@Modifying
@Query("delete from User u where u.role.id = ?1")
void deleteInBulkByRoleId(long roleId);

El derivado ejecuta una consulta y borra cada instancia con CrudRepository.delete(Iterable), así que se ejecutan los callbacks @PreRemove. El bulk lanza una sola sentencia JPQL y las instancias cargadas no reciben callbacks. Borrar muchos objetos los carga todos en memoria hasta el flush o el final de la transacción.

Otros mecanismos

Query hints y comentarios

  • @QueryHints recibe un array de @QueryHint y un flag forCounting que decide si los hints se aplican también a la consulta de conteo de la paginación.
  • @Meta(comment = …) inserta comentarios en las consultas para depurar. En Hibernate hay que activar spring.jpa.properties.hibernate.use_sql_comments=true. En EclipseLink, spring.jpa.properties.eclipselink.logging.level.sql=FINE.

@EntityGraph

Configura el plan de fetch. Su atributo type elige FETCH o LOAD. Se puede referenciar un @NamedEntityGraph o construir el grafo al vuelo con attributePaths.

Java
@Entity
@NamedEntityGraph(name = "GroupInfo.detail",
  attributeNodes = @NamedAttributeNode("members"))
public class GroupInfo {
  @ManyToMany // por defecto, lazy
  List<GroupMember> members = new ArrayList<GroupMember>();
}

public interface GroupRepository extends CrudRepository<GroupInfo, String> {

  @EntityGraph(value = "GroupInfo.detail", type = EntityGraphType.LOAD)
  GroupInfo getByGroupName(String name);

  // grafo ad hoc
  @EntityGraph(attributePaths = { "members" })
  GroupInfo getByGroupName(String name);
}

Scroll de resultados grandes

Hay tres opciones: paginar, hacer scroll por offset (más ligero, no necesita conteo total) o scroll por keyset (usa índices de la base de datos). No funciona con consultas basadas en String ni con métodos @Procedure. Devuelve un Window<T>.

Java
Window<User> users = repository.findFirst10ByLastnameOrderByFirstname("Doe", ScrollPosition.offset());
do {
  for (User u : users) {
    // consumir el usuario
  }
  if (users.isLast() || users.isEmpty()) {
    break;
  }
  users = repository.findFirst10ByLastnameOrderByFirstname("Doe", users.positionAt(users.size() - 1));
} while (!users.isEmpty());

// o con WindowIterator
WindowIterator<User> users = WindowIterator.of(position -> repository.findFirst10ByLastnameOrderByFirstname("Doe", position))
  .startingAt(ScrollPosition.offset());
  • ScrollPosition marca la posición exacta de un elemento y se trata como exclusiva: los resultados empiezan después de ella.
  • Con keyset, las propiedades de ordenación deben ser no nulas y aparecer en el resultado. La clave primaria se añade sola para que el orden sea único.

QueryRewriter

Permite modificar la consulta justo antes de llegar al EntityManager, incluida la de conteo. Se implementa QueryRewriter, se registra como bean y se enlaza con el atributo queryRewriter de @Query o @NativeQuery.

Otras vías para consultas complejas

  • Un @Query a mano.
  • Una implementación de repositorio personalizada con EntityManager, la API Criteria o JdbcTemplate.
  • Una consulta guardada en la base de datos como procedimiento (@StoredProcedure) o función invocada con @Query y CALL.
